# v0.3.1: リンク・強調で文章が崩れる問題

## 原因

v0.3.0はDOMのテキストノードごとに翻訳していた。例えば `Layered agent memory for <a>DeepSeek Harness</a>, with a nightly pass that <strong>corrects</strong> what the agent got wrong.` は、リンクや太字の前後で別の翻訳になっていた。英語と日本語では語順が異なるため、断片ごとの訳を元の位置へ戻すだけでは文が崩れる。

同じ実モデルでも、段落をまとめて渡すとこの分断を改善できた。したがって、報告された問題には拡張側の分割方法が大きく影響している。一方、nightly passを「ナイトリーパス」、forcing functionを「強制関数」とするような用語の選択はモデル由来の問題として残る。

## 変更

- 段落・見出し・リスト項目・表セル等の中で、リンク・強調・インラインコードを含む文章をまとめて翻訳する。
- インライン要素は番号付きの書式マーカーに変換する。モデルの応答はマーカーの過不足・重複・入れ子関係を検証し、元のDOM要素と新しいテキストノードだけで反映する。モデル生成HTMLは挿入しない。
- リンクのhrefやイベントリスナーは元の要素に残す。code/kbd/sampの内容は、モデルが書き換えて返しても原文を維持する。
- 応答中に書式マーカーが欠落した場合や、ページが先に書き換わった場合は、壊れた訳文を反映しない。原文復元にも対応する。
- タイトルと導入段落から最大400文字の文脈を添える。同じ単語でも文脈が異なればキャッシュを分離する。

対象にできない複雑な構造や、書式マーカー込み1200文字を超える段落は従来のテキスト処理を使う。全ページの語順や訳語を保証する変更ではない。

## 回帰テスト

- `npm test`: 23件。文脈ごとのキャッシュ分離、PFMLへの文脈渡し、マーカー途中で分割しないこと等を含む。
- `npm run test:dom`: 実Chromiumで7件。ここでは推論を固定応答にし、段落全体の送信、リンクの並べ替えと同一要素・クリック処理の保持、コード保護、書式欠落・重複の拒否、サイトの再描画との競合、生成HTMLを実行しないこと、コードだけ／日本語の段落を変更しないことを検証する。CIでも実行する。
- `npm run test:e2e`: 実モデルを使用し、通常の7ケースに上記READMEのHTMLを含む。`E2E_LIVE=1`ではExample.com・CERN・IANA・MDNも確認する。

更新時は拡張を再読み込みし、対象のWebページも再読み込みすること。古い断片訳のキャッシュは新しい文脈付きキーでは再利用しない。
